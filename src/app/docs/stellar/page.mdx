# Stellar

Stellar is the planned settlement network for Feyo. Its low-cost, fast transactions and stablecoin ecosystem make it a strong fit for payment infrastructure, while the application still needs careful handling of authorization, assets, fees, and network configuration.

## Planned transaction lifecycle

Feyo will model a payment from intent to verification:

- identify the asset, issuer, network, and destination;
- validate the authorized amount and recipient;
- construct and sign through an explicitly controlled wallet boundary;
- submit the transaction to Stellar infrastructure;
- verify the resulting transaction and expose its status.

## Current status

The repository integrates Freighter wallet connection on Stellar Testnet for the `/app` workspace without initiating payments or transactions. No private keys are stored or managed by the application; only the public account address (`G...`) is queried.

A read-only Testnet balance service is also implemented under `src/lib/stellar/`. It queries Horizon for public account data and never signs or submits a transaction. The `/app` workspace can also inspect a known transaction hash against user-supplied expected payment details, but Feyo still cannot construct, sign, or submit that transaction.

## Read-only Testnet balances

The balance service validates a public address before any request, normalizes native and issued balances, and reports failures explicitly instead of returning partial data. It is **Testnet, read-only**.

```ts
import { fetchTestnetAccountBalances } from "@/lib/stellar/account-balances";

const result = await fetchTestnetAccountBalances("G...");

if (result.ok) {
  for (const balance of result.value.balances) {
    // Native XLM: kind === "native" and code === "XLM".
    // Issued assets: kind === "issued" with both code and issuer.
    // Do not assume every issued asset is USDC.
  }
} else {
  // result.error.code distinguishes the failure modes below.
}
```

| Error code | Meaning |
| --- | --- |
| `invalid_address` | The input is not a valid Stellar public key. No request is made. |
| `unfunded_account` | Horizon returned 404; the account is not funded on Testnet. |
| `network_error` | The request could not reach Horizon. |
| `endpoint_unavailable` | Horizon returned a non-404 error status, available as `httpStatus`. |
| `malformed_response` | The payload did not match the expected account shape. |

Balances remain decimal strings so no floating-point conversion occurs. Issued assets retain their asset code and issuer, and unsupported asset types (such as liquidity pool shares) are rejected as malformed rather than being given an invented identity. Tests inject a mocked `fetch`; CI requires no live network access.

## Read-only Testnet payment verification

`verifyTestnetPayment()` is locked to the Stellar Testnet passphrase and uses the official Testnet Horizon URL by default. Its network client is injectable so CI can use deterministic evidence without funds or a live endpoint.

Verification requires both a successful transaction record and a successful classic `payment` operation in that transaction. The operation must exactly match the expected source, destination, integer stroop amount, and asset identity. Issued assets match both code and issuer. A successful but unrelated transaction is `mismatched`, not verified.

Typed outcomes keep uncertainty explicit:

| Outcome | Meaning |
| --- | --- |
| `verified` | Successful ledger transaction and one exact payment operation matched. |
| `not_found` | Horizon does not currently record the hash; it may be pending or absent. |
| `failed` | Horizon recorded the transaction as failed. |
| `mismatched` | The transaction succeeded, but no payment operation matched every expected field. |
| `invalid_request` | Hash, account, amount, asset, or network input was rejected before lookup. |
| `unavailable` | Transaction or operation evidence could not be retrieved. |
| `malformed` | Horizon returned an unexpected payload, so verification failed closed. |

Verified evidence has runtime provenance: a plain object, copied object, serialized object, or caller-provided `paymentMatched` boolean cannot authorize the `Verified` UI state. Persisted records must be reverified against Horizon before they can regain verified status. A request guard is available so account, hash, or intent changes invalidate stale asynchronous responses.

The workspace validates every field before lookup, limits each verification to 10 seconds, allows cancellation, and aborts stale requests when form, wallet, or network context changes. It distinguishes verified, failed, mismatched, not-found, malformed, invalid, and unavailable outcomes. A safe Stellar Expert Testnet link is shown only for a syntactically valid hash when transaction evidence is available.

### Optional live public-evidence check

The default tests use deterministic fixtures. To manually check a genuine public Testnet payment without creating or funding one, provide its public ledger fields and run:

```bash
FEYO_LIVE_TESTNET_VERIFY=1 \
FEYO_TESTNET_TRANSACTION_HASH=<64-character-hash> \
FEYO_TESTNET_SOURCE=<G...> \
FEYO_TESTNET_DESTINATION=<G...> \
FEYO_TESTNET_AMOUNT=<exact-decimal> \
npm run test:live:testnet
```

For issued assets, also set `FEYO_TESTNET_ASSET_TYPE=issued`, `FEYO_TESTNET_ASSET_CODE`, and `FEYO_TESTNET_ASSET_ISSUER`. All inputs are public and sent only to official Testnet Horizon. Never provide a secret key or recovery phrase.


## Freighter setup and testnet smoke test

To test the wallet connection locally with Freighter:

1. **Install Freighter**: Download the browser extension from [Freighter](https://www.freighter.app/).
2. **Switch to Testnet**: Open Freighter settings -> **Network**, and ensure **Test Net** is selected (`Test SDF Network ; September 2015`).
3. **Fund Test Account**: Generate or fund a test account using [Stellar Friendbot](https://laboratory.stellar.org/#account-creator?network=test). Testnet lumens have no real monetary value.
4. **Connect in `/app`**: Navigate to `/app` in your browser and select **Connect Freighter**. Approve the connection request in the Freighter dialog.
5. **Verify Safety Boundaries**: Test connecting with Freighter switched to Mainnet to verify that an unsupported network error is raised safely. Test declining authorization to verify error recovery. Disconnecting resets local session state without falsely claiming wallet permissions were revoked.

## Safety notes

Network, asset issuer, destination, and amount must be treated as security-sensitive inputs. Any future integration needs test coverage for malformed addresses, wrong-network assets, authorization scope, duplicate requests, and failed or pending transactions.
