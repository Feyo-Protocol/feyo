# Architecture

Feyo is designed as a set of explicit boundaries around a payment intent. A request should be understandable before it is authorized, and its final state should be verifiable after submission.

## Intended flow

1. Validate a payment intent with exact amount, asset identity, destination, network, and idempotency metadata.
2. Read the source account, recipient readiness, sequence, and current fee context from Testnet infrastructure.
3. Build a bounded unsigned classic-payment preview that says `Not signed · Not submitted`.
4. Require deliberate user approval, then recheck the wallet account and Testnet passphrase before asking the wallet to sign.
5. Treat the wallet signature as authorization only: `Signed · Not submitted`.
6. Submit through a controlled Testnet boundary and record the exact transaction hash without claiming settlement.
7. Independently query Horizon for the transaction and its operations.
8. Present `Verified` only when successful ledger evidence contains the exact expected payment operation.

Steps 1 and 7-8 exist today, including a read-only `/app` interface for checking a known Testnet hash against expected payment details. Recipient readiness, unsigned construction, signing, and submission remain separate future milestones.

## Trust model

Feyo should not need to hold a user's private key to coordinate a payment. Authorization, signing, provider access, and verification must remain separable so that each can be reviewed and replaced independently.

Feyo must never ask for, receive, log, or persist a wallet recovery phrase or secret key. The browser wallet remains the signing boundary. Public addresses, transaction hashes, and ledger activity are public but still privacy-sensitive because they are linkable; logs and analytics should collect no signed XDR or unnecessary wallet/session metadata.

The design fails closed against malformed Horizon data, wrong networks, wrong accounts, asset-code or issuer substitution, amount rounding, stale browser responses, unrelated operations, failed transactions, and caller-fabricated verification flags. Testnet verification currently trusts one configured Horizon view and is not proof of off-chain delivery, fiat payout, or Mainnet settlement.

## Sequences, fees, time bounds, and retries

A future builder must fetch a fresh source account sequence and treat it as single-use transaction context. Building advances the SDK account object's in-memory sequence, so abandoned previews must reload the account before building another transaction. Classic fees are per operation; the preview must show the selected fee in stroops and enforce a reviewed upper bound. Every payment must use a finite time bound so stale authorization expires, and the Testnet passphrase must be supplied explicitly during construction and rechecked before signing.

Submission retries must be hash-centric. Persist an intent fingerprint, idempotency key, signed envelope identity, sequence, and transaction hash before network submission. If Horizon returns a timeout or the connection drops, the outcome is ambiguous: query the exact hash and, if resubmission is required, resend the identical signed envelope. Do not rebuild with a new sequence or create a second signature while the first hash may still land. Only after the original hash is definitively failed or expired, and independent verification confirms it did not settle, may a deliberate new attempt load a fresh sequence and receive a new attempt identifier.

`Submitted` means only that a submission call was attempted or acknowledged. `Confirming` means the exact hash is awaiting trustworthy evidence. Neither state is `Verified`.

This page describes the target architecture, not a claim that those components are already running in production.
